# K12 — ForgeGraphics, Display Foundation, and Workplace Shell Boundary

K12 is Titanweave's first graphics/display milestone. It begins from the frozen,
QEMU-qualified K11 tree and does **not** replace K11's hardware, scheduling,
storage, trust, or userspace foundations.

## K12 goals

1. Capture a standards-compliant UEFI GOP linear framebuffer in TitanBoot and
   hand it to WeaveCore through boot protocol v12.
2. Provide a bounds-checked firmware-framebuffer fallback so boot diagnostics
   and recovery remain visible before a native GPU driver exists.
3. Establish **ForgeGraphics ABI v1**, a backend-neutral graphics contract for
   firmware GOP, VirtIO-GPU, AMD, Intel, NVIDIA, and future multi-GPU paths.
4. Establish compositor safety semantics: owned surfaces, z-order, clipping,
   damage tracking, destruction, and hit testing.
5. Establish input-routing semantics above K11 HID decoding: keyboard focus,
   pointer focus, pointer capture, sequencing, and bounded queues.
6. Start the persistent native `DISPLAYD.ELF` service and expose the primary
   display through the Titanweave syscall ABI.
7. Preserve a headless boot mode. Graphics failure must never prevent recovery,
   serial diagnostics, storage access, or native services from starting.
8. Render a deterministic Workplace Shell reference preview in the firmware
   framebuffer for QEMU qualification.

## Architecture boundary

The kernel owns:

- display memory protection and scanout arbitration;
- graphics-device capability checks;
- safe surface metadata and ownership;
- input focus/capture policy;
- fallback framebuffer rendering needed for boot/recovery;
- the stable ForgeGraphics ABI.

`DISPLAYD` owns the long-term desktop composition policy. Native GPU drivers
bind through ForgeBus/ForgeGraphics. The permanent Workplace Shell must not
require application-specific drawing code in WeaveCore.

## Firmware framebuffer policy

The UEFI loader prefers the largest direct RGB/BGR GOP mode no larger than
2560x1440. PixelBltOnly and unsupported bitmask modes are rejected for
post-ExitBootServices rendering. If no usable linear mode exists, K12 logs the
condition and continues headless.

The GOP framebuffer is a compatibility/fallback backend, **not** a substitute
for a native accelerated driver.

## ForgeGraphics v1 capability model

Initial capability bits cover:

- scanout;
- blit;
- compute;
- timeline fences;
- shared memory;
- multi-GPU copy.

Backend identities are explicitly distinct for firmware framebuffer,
VirtIO-GPU, AMD native, Intel native, and NVIDIA native drivers. This keeps the
compositor contract stable when acceleration arrives.

## Workplace Shell visual contract

The canonical K12 visual reference is
`docs/design/WORKPLACE_SHELL_REFERENCE.png`. K12's qualification renderer must
preserve the major composition:

- dark navy top system/status bar;
- left Workplace Navigator / quick-launch / system-status rail;
- blue-steel desktop field and Titanweave branding area;
- dense OS/2-inspired framed utility windows with blue title bars;
- bottom taskbar with Start area, running-window buttons, and status tray;
- information-dense panels suitable for artists, DJs, gamers, developers, and
  administrators rather than a phone-like launcher UI.

The exact bitmap artwork is a resource-layer concern. K12's kernel fallback
uses geometric branding and layout so the graphics path remains testable even
without packaged visual assets.

## K12 qualification markers

A successful K12 QEMU run should emit, at minimum:

- `[BOOT] WeaveCore K12 entered from WEAVECORE.ELF`
- `[GFX ] K12 GOP scanout online:` (or explicit headless fallback in a headless test)
- `[COMP] surface/damage self-test:`
- `[INPT] focus/capture self-test:`
- `[FGFX] ForgeGraphics ABI v1 backend contract passed`
- `[WPS ] Workplace Shell reference preview rendered:`
- `[USER] Starting disk-backed K12 native services`
- `[USER] [displayd] K12 display/compositor service online`
- `[KERN] K12 alive:`
- `[QUAL] K12 runtime reached intentional post-userspace halt`
- `[HALT] BSP halted intentionally`

K12 QEMU qualification does not equal production GPU-driver completion. Native
AMD/Intel/NVIDIA acceleration, display hot-plug, EDID, multiple monitors,
color-management, VRR/HDR, protected surfaces, and multi-GPU scanout require
subsequent hardware-specific milestones.
